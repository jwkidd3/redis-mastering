Building Production-Grade Distributed Redis

Why Redis Cluster?

Single Instance Limitations

  • Memory constraints — capped at one machine's RAM
  • CPU bottlenecks — single-threaded command execution
  • Single point of failure
  • No horizontal scaling

Cluster Benefits

  • Linear scalability across masters
  • Automatic failover with replicas
  • Data sharding via hash slots
  • Continued availability during node loss

Sharding with Hash Slots

Redis Cluster distributes keys across 16384 hash slots.
Slot = CRC16(key) % 16384. Each master owns a contiguous slot range.
Keys wrapped in {...} hash to the tag only — so {customer:123}:profile and {customer:123}:policies land on the same slot.
KeyHash SlotMaster
user:1235649Master-2
product:45611589Master-3
{customer:789}:profile3421Master-1
{customer:789}:orders3421Master-1

Hash tags {} keep related keys co-located for multi-key operations and pipelines.

Master-Replica Replication

  • Masters accept writes; replicas receive updates asynchronously
  • Read scaling possible via replica reads
  • Automatic promotion on master failure
  • Typical lag <1s under normal load
# Per-replica state INFO replication # Verify lag from a replica ROLE # returns master repl offset # Compare master_repl_offset on master vs slave_repl_offset on replica
Replication is asynchronous — a crashed master can lose a few unreplicated writes. For the strongest RPO, combine with AOF appendfsync always.

Automatic Failover

1. Detection (5-15 seconds)
Peer nodes mark master PFAIL, then FAIL after gossip consensus
2. Election
A replica of the failed master requests votes from other masters
3. Promotion
Winning replica becomes new master and claims the slot range
4. Reconfiguration
Cluster propagates updated slot-to-node map via gossip
5. Recovery
Old master rejoins as a replica of the new master when it returns
Typical end-to-end failover: ~15 seconds with cluster-node-timeout 5000.

Troubleshooting Cluster Issues

CLUSTERDOWN: Uncovered slots — run redis-cli --cluster fix
MOVED loops: Client has a stale slot map — confirm cluster-aware client and version
CROSSSLOT errors: Multi-key op hitting different slots — add hash tags to co-locate
Replication lag: Check network, replica CPU, client-output-buffer-limit for replicas
Uneven slot distribution: Run redis-cli --cluster rebalance
# Most useful diagnostic triad redis-cli -p 9000 CLUSTER INFO redis-cli -p 9000 CLUSTER NODES redis-cli --cluster check 127.0.0.1:9000

Production Best Practices

Configuration

  • cluster-node-timeout: 5000-15000 ms
  • cluster-replica-validity-factor: 10
  • cluster-migration-barrier: 1 (keep at least 1 replica per master)
  • cluster-require-full-coverage: no (stay available on partial failure)

Operations

  • Start with 6 nodes on separate hosts / availability zones
  • Plan for ~30% headroom; monitor slot distribution
  • Rolling upgrades, regular backups, periodic failover drills
  • Enable TLS between nodes; use ACLs for client access

Common Pitfalls

Avoid

  • Cross-slot multi-key ops without hash tags
  • Assuming strong consistency across masters
  • Ignoring replication lag in read-after-write flows
  • Uneven slot distribution after reshards
  • Running cluster with no failure testing

Do Instead

  • Design key schema with hash tags ({customer:123}:*)
  • Read from master or wait for replication on critical reads
  • Rebalance after topology changes; watch CLUSTER COUNTKEYSINSLOT
  • Run chaos tests (kill nodes, partition the network) regularly

Key Takeaways

  • Redis Cluster gives horizontal scale without an external proxy
  • 16384 hash slots + CRC16 drive deterministic key placement
  • Replicas + automatic failover keep each slot range available
  • Hash tags {...} keep related keys co-located for multi-key ops
  • Cluster chooses availability on partition — design for eventual consistency
  • Monitor cluster state, slot coverage, and replication lag continuously
