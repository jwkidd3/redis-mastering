Core Data Structures

String Operations & Key Management

Duration: 30 minutes

Focus: Redis String data type and operations

Redis String Data Type

  • Binary-safe — can store any data type
  • Maximum size: 512 MB per string
  • Most basic Redis data type
  • Versatile: text, numbers, JSON, binary data
# String can hold various data types SET policy:123456 "AUTO-2024-PREMIUM-1500" SET customer:789012 "John Smith" SET claim:amount:456 "2500.50"

Basic String Operations — SET & GET

  • SET — Store key-value pairs
  • GET — Retrieve values by key
  • EXISTS — Check if key exists
  • DEL — Delete keys
# Store policy information SET policy:123456 "AUTO-PREMIUM-1500-ACTIVE" # Retrieve policy data GET policy:123456 # Check existence EXISTS policy:123456 # Delete policy DEL policy:123456

SET Command Options

  • SET key value EX seconds — Set with expiration
  • SET key value NX — Set if not exists
  • SET key value XX — Set if exists
  • SETNX — Set if not exists (standalone)
# Set with 1 hour expiration SET quote:temp:789 "QUOTE-DATA" EX 3600 # Set only if customer doesn't exist SET customer:new:456 "New Customer" NX # Update only if policy exists SET policy:123456 "UPDATED-STATUS" XX

Numeric Operations

  • INCR — Increment by 1
  • DECR — Decrement by 1
  • INCRBY / DECRBY — By specified amount
  • INCRBYFLOAT — Increment by float value
# Initialize claim counter SET claim:counter 0 # Increment for new claims INCR claim:counter # Returns: 1 INCR claim:counter # Returns: 2 # Add premium amount SET premium:total 0 INCRBY premium:total 1500 # Add $1500 INCRBYFLOAT premium:total 250.50 # Add $250.50

String Manipulation Commands

  • APPEND — Append to existing string
  • STRLEN — Get string length
  • GETRANGE — Get substring
  • SETRANGE — Overwrite part of string
# Build policy number incrementally SET policy:temp "AUTO" APPEND policy:temp "-2024" # "AUTO-2024" APPEND policy:temp "-PREMIUM" # "AUTO-2024-PREMIUM" # Get string length STRLEN policy:temp # Returns: 17 # Extract year from policy number GETRANGE policy:temp 5 8 # Returns: "2024"

Batch Operations — MSET & MGET

  • MSET — Set multiple keys atomically
  • MGET — Get multiple values at once
  • MSETNX — Set multiple if none exist
  • Benefit: Reduced network round trips
# Set multiple customer data points MSET customer:123:name "John Smith" \ customer:123:email "john@email.com" \ customer:123:status "ACTIVE" # Retrieve multiple values MGET customer:123:name customer:123:email customer:123:status

Key Naming Conventions

  • Hierarchical structure: Use colons (:) as separators
  • Entity-based: Start with entity type
  • Consistent patterns: Predictable key structure
  • Case sensitivity: Redis keys are case-sensitive
# Entity-based naming patterns policy:123456:premium # Policy premium amount policy:123456:status # Policy status customer:789012:profile # Customer profile data customer:789012:policies # Customer's policies claim:456789:amount # Claim amount claim:456789:status # Claim processing status

TTL (Time To Live) Management

  • EXPIRE — Set expiration in seconds
  • EXPIREAT — Set expiration at Unix timestamp
  • TTL — Check remaining time
  • PERSIST — Remove expiration
  • PEXPIRE/PTTL — Millisecond precision
# Set quote with 30-minute expiration SET quote:temp:789 "QUOTE-DATA-HERE" EXPIRE quote:temp:789 1800 # Check remaining time TTL quote:temp:789 # Returns seconds remaining # Remove expiration (make permanent) PERSIST session:user:456

Atomic SET with Expiration (SETEX)

  • SETEX — Set value + TTL in seconds (atomic)
  • PSETEX — Same, in milliseconds
  • SET key val EX sec — Equivalent modern syntax
  • Use cases: Sessions, tokens, rate limiting
# SETEX - Atomic set with seconds TTL SETEX session:user:123 3600 "user-session-data" # Equivalent modern syntax (can combine with NX) SET session:user:123 "user-session-data" EX 3600 SET lock:resource "worker-1" EX 30 NX # Wrong way - NOT atomic (crash between = no TTL!) SET token:temp "TOKEN-VALUE" EXPIRE token:temp 60
Best Practice: Always use atomic variants for temporary data.

Memory Optimization Strategies

  • Key length: Shorter keys save memory
  • Value encoding: Redis optimizes small integers/strings
  • Expiration policies: Automatic cleanup
  • Monitor with MEMORY USAGE: Check per-key memory
# Memory-efficient key naming # Instead of: customer:profile:personal:full:name:first # Use: cust:123:fname # Check memory usage of specific keys MEMORY USAGE policy:123456 MEMORY USAGE customer:789012:profile

Common String Patterns

  • Session storage: User login tokens
  • Caching: API responses and computed values
  • Counters: Unique ID generation with INCR
  • Distributed locking: SETNX for simple locks
  • Rate limiting: INCR with TTL
# API response caching SET cache:policy:123456 '{"policy":"data","premium":1500}' EX 300 # Rate limiting counter SET rate:limit:user:789 "1" EX 60 INCR rate:limit:user:789 # Increment usage # Unique ID generation INCR policy:id:generator # Returns: 1, 2, 3, ... # Simple distributed lock SET lock:process:claims "worker-1" EX 30 NX

Introduction to Sets for Tracking

  • Sets — Collections of unique strings
  • SADD — Add members to a set
  • Use case: Track unique items (active sessions, processed IDs)
  • Coming in Day 2: Full coverage of sets and sorted sets
# Track unique processed claim IDs SADD processed:claims "CLAIM-001" SADD processed:claims "CLAIM-002" SADD processed:claims "CLAIM-001" # Duplicate ignored # Track active sessions SADD sessions:active "session:123" "session:456"

Persistence & Backup Monitoring

  • LASTSAVE — Unix timestamp of last RDB save
  • BGSAVE — Non-blocking background save
  • INFO persistence — Full persistence status
  • Use case: Monitor backup freshness in production
# Check when last backup occurred LASTSAVE # Returns: 1699564800 (Unix timestamp) # Trigger manual backup (non-blocking) BGSAVE # Full persistence details INFO persistence # Shows: rdb_last_save_time, rdb_bgsave_in_progress, etc.
