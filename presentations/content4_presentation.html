Why Redis from Node.js?

Natural Fit

  • Both are event-driven and non-blocking
  • JSON-friendly data model
  • Single-threaded event loop pairs well with single-threaded Redis
  • Modern async/await API in the official client

Insurance Use Cases

  • Customer portals with sub-ms reads
  • Policy and claims caching
  • Session state for agent dashboards
  • Real-time rate lookups
Result: Reduce database load 70-90% and cut typical response times from ~100ms to <5ms.

The Official Node.js Redis Client

  • Package: redis (node-redis v4+)
  • API style: Promise-based, camelCase commands (hGetAll, zAdd)
  • Features: Auto-reconnect, TLS, cluster support, Pub/Sub, Streams
  • Alternatives: ioredis - similar API, preferred for Redis Cluster
Course standard: We use redis for Labs 6-9. Syntax in labs matches this presentation.

Installing and Connecting

Install the official redis client and open a connection with event handlers.

npm install redis
const redis = require('redis'); const client = redis.createClient({ url: 'redis://your-redis-host:6379' }); client.on('error', (err) => console.log('Redis Client Error', err)); client.on('connect', () => console.log('Connected to Redis')); await client.connect();
Always attach an error listener before connect() to avoid unhandled exceptions.

Insurance Key Naming Conventions

Use colon-delimited, predictable keys so you can reason about data ownership and invalidate cleanly.

  • customer:1001 - hash of customer fields
  • customer:1001:claims - list of claim IDs
  • policy:POL-001 - policy record (hash or JSON)
  • claims:queue:auto - processing queue
  • leaderboard:agents:q1 - sorted set
Benefit: Consistent patterns let you target invalidation, run SCAN safely, and debug in Redis Insight.

Async/Await - Customer & Policy Operations

Modern Redis operations return promises. Use await for clean, readable code.

// Store a customer profile await client.hSet('customer:1001', { name: 'John Doe', email: 'john.doe@example.com', tier: 'premium' }); // Store a policy as JSON const policy = { id: 'POL-001', type: 'auto', premium: 1200.50, status: 'active' }; await client.set('policy:POL-001', JSON.stringify(policy)); // Retrieve data const customer = await client.hGetAll('customer:1001'); const rawPolicy = await client.get('policy:POL-001'); console.log(customer.name, JSON.parse(rawPolicy).premium);

Parallel Operations with Promise.all

When operations are independent, run them in parallel to cut total latency.

async function getCustomerDashboard(customerId) { const [profile, claims, policies] = await Promise.all([ client.hGetAll(`customer:${customerId}`), client.lRange(`customer:${customerId}:claims`, 0, 9), client.sMembers(`customer:${customerId}:policies`) ]); return { profile, recentClaims: claims, activePolicies: policies }; }
Rule of thumb: Use Promise.all when later calls don't depend on earlier results. Use sequential await when they do.

Connection Pooling for Production

Node.js apps typically share a single client across the process. For high-throughput services, use a pool so independent requests don't serialize on one socket.

const { createPool } = require('generic-pool'); const redis = require('redis'); const pool = createPool({ create: async () => { const client = redis.createClient({ url: 'redis://your-redis-host:6379' }); await client.connect(); return client; }, destroy: async (client) => client.quit() }, { min: 2, max: 20 }); async function getCustomer(id) { const client = await pool.acquire(); try { return await client.hGetAll(`customer:${id}`); } finally { pool.release(client); } }
Guideline: Pool size should match expected concurrent Redis operations, not total requests.

Error Handling Pattern

Wrap Redis calls so transient failures degrade gracefully instead of crashing requests.

async function safeGetPolicy(policyId) { try { const raw = await client.get(`policy:${policyId}`); return raw ? JSON.parse(raw) : null; } catch (error) { console.error(`Redis error for policy ${policyId}:`, error.message); if (error.code === 'ECONNREFUSED') { // Redis is down - fall back to the primary database return await db.getPolicy(policyId); } throw error; } }
Principle: Treat the cache as an optimization, not a source of truth. Your app must still work if Redis is unreachable.

TTL for Ephemeral Insurance Data

Set expirations on cached reads and session data so stale entries clean themselves up.

// Cache a policy lookup for 1 hour await client.setEx( `policy:${policyId}`, 3600, JSON.stringify(policyData) ); // Session token - 30 minutes, sliding window await client.setEx(`session:${token}`, 1800, userId); // Rate-limit counter - resets every 60 seconds await client.incr(`ratelimit:${userId}`); await client.expire(`ratelimit:${userId}`, 60);
Tip: SETEX is atomic - it sets the value and TTL in one round trip.

Graceful Shutdown

Close Redis connections cleanly on process exit so in-flight commands aren't dropped.

process.on('SIGTERM', async () => { console.log('Shutting down...'); try { await client.quit(); // finishes pending commands console.log('Redis connection closed'); } catch (err) { await client.disconnect(); // force close } process.exit(0); });
Difference: quit() waits for pending replies. disconnect() terminates immediately - use only if quit() fails.
