Redis Hashes - Structured Records

What are Hashes?

  • Field-value pairs under a single key
  • Perfect for object-like structures
  • Memory efficient for small-to-medium objects
  • Partial updates and atomic per-field operations

Insurance Applications

  • Customer Profiles: Name, contact, tier
  • Policy Records: Coverage, premium, status
  • Claims Data: Amount, status, dates
  • Agent Info: Territory, certifications
Key Benefit: Update individual fields without rewriting the entire record.

Hash Operations - Customer Profiles

# Create customer profile (batch set)
HSET customer:12345 name "Alice Johnson" email "alice@example.com" \
    tier "premium" risk_score 850 state "CA"

# Partial update - only touch changed fields
HSET customer:12345 tier "platinum"

# Read single or multiple fields
HGET customer:12345 tier                        # "platinum"
HMGET customer:12345 name email tier            # 3 values
HGETALL customer:12345                          # All fields

# Atomic numeric operations
HINCRBY customer:12345 claim_count 1
HINCRBYFLOAT policy:AUTO-001 premium 25.50

# Existence and management
HEXISTS customer:12345 phone
HDEL customer:12345 temporary_note
HLEN customer:12345
Commands to know: HSET, HGET, HMGET, HGETALL, HINCRBY, HDEL, HEXISTS, HLEN

Hashes vs JSON for Policy Data

Use Hashes When

  • Frequently updated individual fields
  • Numeric counters (claim counts, premiums)
  • Need per-field atomic operations
  • Shallow, flat structure

Use JSON Strings When

  • Complex nested structures (claim w/ multiple adjusters)
  • Immutable or replace-all updates
  • API round-trips with fixed schemas
  • Arrays inside objects
Rule of thumb: Hashes for customer/policy records. JSON for deep claim documents.

Redis Lists - Ordered Collections

What are Lists?

  • Ordered sequences of strings
  • O(1) push/pop at head and tail
  • Support blocking operations (BLPOP)
  • Perfect for queues and audit trails

Insurance Applications

  • Claims processing queue (FIFO)
  • Renewal reminder queue
  • Audit logs (chronological events)
  • Customer activity history
Key Feature: Blocking operations let workers wait efficiently for new work - no polling.

Claims Processing Queue with Lists

# Producer: add new claims to the queue (FIFO)
RPUSH claims:processing "CLAIM-2024-001:fender_bender:2500"
RPUSH claims:processing "CLAIM-2024-002:water_damage:8500"
RPUSH claims:processing "CLAIM-2024-003:theft:15000"

# Urgent lane - jump to front
LPUSH claims:urgent "CLAIM-2024-004:total_loss:35000"

# Monitor queue depth
LLEN claims:processing

# View without removing
LRANGE claims:processing 0 -1

# Consumer: pop the oldest claim
LPOP claims:urgent          # urgent first
RPOP claims:processing      # then oldest regular

# Worker with blocking wait (30-second timeout)
BLPOP claims:urgent claims:processing 30

# Trim audit history to last 100 entries
LPUSH audit:policy:AUTO-001 "premium_updated:2024-03-15"
LTRIM audit:policy:AUTO-001 0 99
Pattern: RPUSH + BLPOP = durable FIFO queue. LPUSH + LTRIM = bounded audit log.

Redis Sets - Unique Collections

What are Sets?

  • Unordered collection of unique strings
  • O(1) add, remove, and membership testing
  • Support set algebra (union/intersect/diff)
  • Automatic de-duplication

Insurance Applications

  • Customer tags: Risk categories, segments
  • Active claimants: Unique IDs only
  • Agent certifications: Skills, licenses
  • Policy features: Coverage types, riders
Key Feature: Native uniqueness + set algebra make Sets ideal for cohort analytics.

Basic Set Operations

# Build risk cohorts (duplicates are ignored automatically)
SADD customers:high_risk "customer:12345" "customer:67890" "customer:11111"
SADD customers:low_risk  "customer:22222" "customer:33333"

# Membership check (O(1))
SISMEMBER customers:high_risk "customer:12345"   # 1

# Count and list
SCARD customers:high_risk                        # 3
SMEMBERS customers:high_risk

# Move a customer between cohorts
SREM customers:high_risk "customer:12345"
SADD customers:low_risk  "customer:12345"

# Track unique claimants - duplicates collapse
SADD claimants:active "claimant:1001" "claimant:1002" "claimant:1001"
SCARD claimants:active                           # 2
Commands to know: SADD, SREM, SISMEMBER, SMEMBERS, SCARD

Set Algebra - Cross-Sell & Segmentation

# Customers with each policy type
SADD policy:auto:customers "cust:001" "cust:002" "cust:003"
SADD policy:home:customers "cust:002" "cust:003" "cust:004"

# Cross-sell: customers with BOTH auto AND home
SINTER policy:auto:customers policy:home:customers
# => ["cust:002", "cust:003"]

# Upsell target: auto customers without home
SDIFF policy:auto:customers policy:home:customers
# => ["cust:001"]

# Campaign list: anyone with either policy
SUNION policy:auto:customers policy:home:customers

# Store the intersection for later (useful for caching)
SINTERSTORE segment:multi_policy \
    policy:auto:customers policy:home:customers
Lab 9 Preview: These three operations - SINTER, SUNION, SDIFF - are the core of cohort analytics you'll build.

Redis Sorted Sets - Ranked Collections

What are Sorted Sets?

  • Members with a floating-point score
  • Automatically ordered by score
  • Unique members; scores may repeat
  • O(log N) insert and range queries

Insurance Applications

  • Claim rankings by dollar amount
  • Agent leaderboards by sales
  • Risk scores, loyalty points
  • Time-series via timestamps as scores
Key Feature: Score-based ordering with unique membership - leaderboards, priority queues, and time windows in one structure.

Claim Ranking by Amount

# Score = claim amount
ZADD claims:by:amount 2500    "CLAIM-2024-001"
ZADD claims:by:amount 15000   "CLAIM-2024-002"
ZADD claims:by:amount 8500    "CLAIM-2024-003"
ZADD claims:by:amount 125000  "CLAIM-2024-004"

# Top 3 highest-value claims
ZREVRANGE claims:by:amount 0 2 WITHSCORES

# Rank a specific claim
ZREVRANK claims:by:amount "CLAIM-2024-004"   # 0 (1st)

# Claims between $5K and $20K
ZRANGEBYSCORE claims:by:amount 5000 20000 WITHSCORES

# Count claims over $100K
ZCOUNT claims:by:amount 100000 +inf

# Adjust a score (revised estimate)
ZINCRBY claims:by:amount 2500 "CLAIM-2024-001"
Commands to know: ZADD, ZRANGE, ZREVRANGE, ZRANGEBYSCORE, ZRANK, ZINCRBY, ZCOUNT

Agent Performance Leaderboard

# Quarterly sales leaderboard
ZADD agent:sales:q1 125000 "agent:john"
ZADD agent:sales:q1  98000 "agent:sarah"
ZADD agent:sales:q1 156000 "agent:mike"
ZADD agent:sales:q1 142000 "agent:tom"

# Top 3 agents
ZREVRANGE agent:sales:q1 0 2 WITHSCORES
# => mike 156000, tom 142000, john 125000

# Agents over $100K target
ZRANGEBYSCORE agent:sales:q1 100000 +inf WITHSCORES

# Award a mid-quarter bonus (increment score atomically)
ZINCRBY agent:sales:q1 10000 "agent:sarah"

# Time-series variant: timestamps as scores
ZADD claims:timeline 1710432000 "CLAIM-001"
ZADD claims:timeline 1710435600 "CLAIM-002"
# Purge claims older than 30 days
ZREMRANGEBYSCORE claims:timeline 0 $(( $(date +%s) - 2592000 ))

Sets vs Sorted Sets - Picking the Right One

Use Sets When

  • Order doesn't matter
  • You need set algebra
  • Binary membership (in / out)
  • Tags, cohorts, feature flags

Example: Active claimants, policy features

Use Sorted Sets When

  • You need ranking or ordering
  • Score-based range queries
  • Leaderboards or priority queues
  • Time-series data

Example: Agent leaderboards, claim rankings
