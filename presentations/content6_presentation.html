Redis Streams - Event-Driven Foundation

🚀 Modern Event Processing with Redis Streams

Streams provide an immutable, append-only log with built-in consumer groups and real-time processing - the backbone of event-driven insurance systems.

Key Features

  • Immutable log: Events stored permanently
  • Consumer groups: Parallel processing
  • Persistence: Replay and recovery
  • Time-range queries: Historical analysis

Insurance Use Cases

  • Claims audit trails
  • Policy lifecycle events
  • Cache invalidation broadcasts
  • Real-time fraud monitoring

Redis Streams - Core Commands

Command Description Example
XADD Append entry to stream XADD claims * action submitted id 12345
XREAD Read from stream XREAD STREAMS claims 0
XGROUP CREATE Create consumer group XGROUP CREATE claims processors $
XREADGROUP Read as consumer group XREADGROUP GROUP processors worker1 STREAMS claims >
XACK Acknowledge delivery XACK claims processors 1640000000000-0

Event Sourcing with Redis Streams

Why Event Sourcing?

  • Audit Trail: Every state change recorded
  • Replay: Rebuild state from history
  • Analytics: Process events as they occur
  • Compliance: Immutable transaction log

Claim Lifecycle

  • Claim submitted → event logged
  • Claim reviewed → event logged
  • Claim approved → event logged
  • Payment issued → event logged

Each event is immutable and carries full context for replay.

Publishing Claim Events

// Publish a claim submission event
await redis.xadd('claims:events', '*',
    'action', 'claim_submitted',
    'claim_id', 'CLM-78921',
    'policy_id', 'POL-12345',
    'customer_id', 'CUS-456',
    'amount', '4500.00',
    'timestamp', Date.now().toString()
);

// Subsequent lifecycle events
await redis.xadd('claims:events', '*',
    'action', 'claim_reviewed',
    'claim_id', 'CLM-78921',
    'adjuster_id', 'ADJ-21',
    'status', 'approved'
);

await redis.xadd('claims:events', '*',
    'action', 'payment_issued',
    'claim_id', 'CLM-78921',
    'amount', '4500.00'
);
Tip: The * ID lets Redis assign a monotonically increasing timestamp-based ID.

Consumer Groups for Parallel Processing

Why Consumer Groups?

  • Distribute work across workers
  • Each message delivered to one consumer
  • Automatic load balancing
  • Pending list tracks unacknowledged work

Insurance Workflow

  • fraud-checkers: score each claim
  • notifiers: email customers
  • analytics: update dashboards
  • All groups read every event independently
// Create a consumer group starting from the tail
await redis.xgroup('CREATE', 'claims:events', 'fraud-checkers', '$', 'MKSTREAM');

// Worker reads and acknowledges
const events = await redis.xreadgroup(
    'GROUP', 'fraud-checkers', 'worker-1',
    'COUNT', 10, 'BLOCK', 2000,
    'STREAMS', 'claims:events', '>'
);
for (const [stream, messages] of events) {
    for (const [id, fields] of messages) {
        await scoreClaim(fields);
        await redis.xack('claims:events', 'fraud-checkers', id);
    }
}

Part 2: Caching Patterns

Events give us a durable log. Now let's use them to keep caches fresh and fast.

The Performance Challenge: Database queries run in 10-100ms. Redis GET runs in <1ms. A well-designed cache layer cuts DB load 70-90%.

Core Caching Patterns

Cache-Aside

Application reads from cache; on miss, loads from DB and populates cache.

Best for: read-heavy policy lookups

Write-Through

Writes go to cache and DB together. Strong consistency; extra latency.

Best for: premium billing data

Write-Behind

Cache first, DB async. Fast writes but risk of loss.

Risk: data loss on cache failure

Cache-Aside Pattern - Customer Lookup

class CustomerCache {
    constructor(redisClient, dbClient) {
        this.redis = redisClient;
        this.db = dbClient;
    }

    async getCustomer(customerId) {
        const cacheKey = `customer:${customerId}`;

        // Try cache first
        let customer = await this.redis.get(cacheKey);
        if (customer) return JSON.parse(customer);

        // Cache miss - fetch from database
        customer = await this.db.getCustomer(customerId);
        if (customer) {
            await this.redis.setex(cacheKey, 3600, JSON.stringify(customer));
        }
        return customer;
    }

    async updateCustomer(customerId, data) {
        await this.db.updateCustomer(customerId, data);
        await this.redis.del(`customer:${customerId}`); // invalidate
    }
}

Cache Invalidation Strategies

  • Time-based (TTL): Automatic expiration - simplest, but can serve stale data
  • Event-driven: Invalidate on update events via Streams or Pub/Sub
  • Pattern-based: Delete by key pattern (customer:*)
  • Tag-based: Group related keys for bulk invalidation
"There are only two hard things in Computer Science: cache invalidation and naming things." - Phil Karlton
For distributed insurance services, prefer event-driven invalidation - it reuses the event log you built in Part 1.

Event-Driven Cache Invalidation with Streams

class EventDrivenCache {
    async setupEventProcessor() {
        try {
            await this.redis.xgroup('CREATE', 'events',
                'cache-invalidator', '$', 'MKSTREAM');
        } catch (e) { /* group exists */ }
        this.processEvents();
    }

    async processEvents() {
        while (true) {
            const events = await this.redis.xreadgroup(
                'GROUP', 'cache-invalidator', 'worker-1',
                'COUNT', 10, 'BLOCK', 1000,
                'STREAMS', 'events', '>');
            for (const [, messages] of events) {
                for (const [id, fields] of messages) {
                    await this.handleEvent(fields);
                    await this.redis.xack('events', 'cache-invalidator', id);
                }
            }
        }
    }

    async handleEvent(fields) {
        const action = fields[1], entityId = fields[3];
        if (action === 'policy_updated')   await this.redis.del(`policy:${entityId}`);
        if (action === 'customer_updated') await this.redis.del(`customer:${entityId}`);
    }
}
