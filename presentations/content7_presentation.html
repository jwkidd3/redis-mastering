Redis Security Fundamentals

Three Pillars

Authentication: AUTH command, ACL users, strong credentials
Network Security: Bind address, protected mode, firewalls, VPN
Encryption: TLS in transit, disk encryption at rest
Golden Rule: Never expose Redis directly to the internet. Always combine authentication, network segmentation, and encryption.
Insurance context: PII, policy data, and claims details require defense-in-depth to satisfy HIPAA, PCI-DSS, and state insurance regulators.

Authentication: AUTH & ACLs

Legacy AUTH

# redis.conf requirepass "StrongP@ssw0rd!" # Client connects AUTH StrongP@ssw0rd!
Single shared password. Use only for internal, low-risk setups.

ACLs (Redis 6+)

# Define per-user access ACL SETUSER claims_agent on \ >ClaimsP@ss \ ~policy:* ~claim:* \ +@read +hset +hget ACL SETUSER readonly on \ >ReadOnlyP@ss \ ~* +@read
Per-user creds, key pattern ACLs, command allow/deny lists.

Why Redis for Session Management?

Traditional Approaches Fall Short

In-memory (Node.js): lost on restart, not shared across servers
Database: too slow for every request
File system: breaks horizontal scaling

Redis Advantages

  • Sub-millisecond reads at scale
  • Automatic expiration via TTL
  • Shared across every app server
  • Native data structures (Hashes, Sets, Sorted Sets)

Session Storage: Hash Pattern

HSET session:abc123 \ userId "user_456" \ role "agent" \ email "jane@insurer.com" \ loginTime "2026-04-23T09:00:00Z" \ lastActivity "2026-04-23T09:15:00Z" EXPIRE session:abc123 1800 HGET session:abc123 role HGETALL session:abc123
Hash-based storage allows field-level reads/updates without deserializing JSON. TTL + EXPIRE on every access gives you sliding sessions.

Session Manager: Structure

class SessionManager { constructor(redis) { this.redis = redis; this.SESSION_TTL = 1800; // 30 minutes } async createSession(userId, userData) { const sessionId = crypto.randomUUID(); const key = `session:${sessionId}`; await this.redis.hSet(key, { userId, role: userData.role, email: userData.email, loginTime: new Date().toISOString(), lastActivity: new Date().toISOString() }); await this.redis.expire(key, this.SESSION_TTL); await this.redis.sAdd(`user:${userId}:sessions`, sessionId); return sessionId; } }

Session Manager: Lifecycle

async getSession(sessionId) { const key = `session:${sessionId}`; const session = await this.redis.hGetAll(key); if (!session || Object.keys(session).length === 0) return null; await this.redis.hSet(key, 'lastActivity', new Date().toISOString()); await this.redis.expire(key, this.SESSION_TTL); // sliding TTL return session; } async destroySession(sessionId) { const session = await this.getSession(sessionId); if (!session) return; await this.redis.sRem(`user:${session.userId}:sessions`, sessionId); await this.redis.del(`session:${sessionId}`); }
Sliding TTL on getSession keeps active users logged in; destroySession also cleans the multi-device index.

Multi-Device Session Tracking

# User logs in from laptop SADD user:456:sessions "session:laptop_abc123" # Then from mobile SADD user:456:sessions "session:phone_xyz789" # List all active sessions for user 456 SMEMBERS user:456:sessions # "Log out of all devices" security feature SMEMBERS user:456:sessions # get all DEL session:laptop_abc123 session:phone_xyz789 DEL user:456:sessions
Insurance use case: An agent reports a lost phone — one call triggers "logout everywhere" to revoke every active session across devices.

Role-Based Access Control (RBAC)

Customer: view own policies, submit claims
Agent: view customer data, process claims
Admin: full access, user management, audits
class RBACManager { constructor(redis) { this.redis = redis; this.permissions = { customer: ['view_own_policy', 'submit_claim'], agent: ['view_customer_data', 'process_claims'], admin: ['*'] }; } async hasPermission(sessionId, permission) { const s = await this.redis.hGetAll(`session:${sessionId}`); const perms = this.permissions[s?.role] || []; return perms.includes('*') || perms.includes(permission); } }

Security Monitoring: Failed Logins

class SecurityMonitor { constructor(redis) { this.redis = redis; this.MAX_ATTEMPTS = 5; this.LOCKOUT = 900; // 15 min } async recordFailedLogin(userId) { const key = `failed_login:${userId}`; const attempts = await this.redis.incr(key); if (attempts === 1) await this.redis.expire(key, 300); if (attempts >= this.MAX_ATTEMPTS) { await this.redis.set(`locked:${userId}`,'1','EX',this.LOCKOUT); } return attempts; } async isLocked(userId) { return !!(await this.redis.get(`locked:${userId}`)); } }
Pattern: counter + TTL for attempts, lock key + TTL for lockouts.

Why Rate Limiting Matters

Brute force: attackers cycle thousands of passwords per second
API abuse: one greedy client degrades service for everyone
DDoS: flood of requests overwhelms app and database
Cost overruns: runaway API calls spike cloud bills
Data scraping: competitors extract policy/pricing data
Real scenario: A single abusive client at 10,000 req/min can easily cost $1000+ per day in cloud infrastructure.

Sliding Window with Sorted Sets

# Sorted set of request timestamps ZADD requests:u123 {ts1} "req1" ZADD requests:u123 {ts2} "req2" # Count requests in last 60s ZCOUNT requests:u123 (now-60000) now # Drop old entries ZREMRANGEBYSCORE requests:u123 0 (now-60000)
Sliding window beats fixed window: no burst exploit at bucket boundaries. Smooth enforcement, per-user limits.
Fixed-window burst problem: 100 calls at 0:59 + 100 at 1:00 = 200 calls in 2 seconds — bypasses a naive per-minute counter.

Sliding Window: Algorithm

Key: sorted set ratelimit:<user>, score = request timestamp.
Step 1: ZREMRANGEBYSCORE drops entries older than now - window.
Step 2: ZCARD returns the count in the current window.
Step 3: if under limit, ZADD the new timestamp; else reject.
Step 4: EXPIRE the key to prevent leaks for idle users.
All four commands run in a single pipeline so they're effectively atomic per request.

Sliding Window: Code

class RateLimiter { constructor(redis, { limit, window }) { this.redis = redis; this.limit = limit; this.window = window; // seconds } async checkLimit(userId) { const key = `ratelimit:${userId}`; const now = Date.now(); const windowStart = now - this.window * 1000; const p = this.redis.pipeline(); p.zRemRangeByScore(key, 0, windowStart); p.zCard(key); p.zAdd(key, { score: now, value: `${now}` }); p.expire(key, this.window); const results = await p.exec(); const count = results[1][1]; if (count >= this.limit) { await this.redis.zRem(key, `${now}`); return { allowed: false, retryAfter: this.window }; } return { allowed: true, remaining: this.limit - count - 1 }; } }

Tier-Based Rate Limits

const RATE_LIMITS = { trial: { limit: 20, window: 60 }, basic: { limit: 50, window: 60 }, standard: { limit: 100, window: 60 }, premium: { limit: 500, window: 60 }, enterprise: { limit: 10000, window: 60 } }; app.post('/api/quote', async (req, res) => { const user = await getUser(req.userId); const limiter = new RateLimiter(redis, RATE_LIMITS[user.tier]); const result = await limiter.checkLimit(req.userId); if (!result.allowed) return res.status(429) .json({ error: 'Too many requests', retryAfter: result.retryAfter }); // ... generate insurance quote });
Insurance use case: Trial users get 20 quotes/min; enterprise partners get 10,000/min.

Abuse Detection & DDoS Defense

Layered Defense

Edge / CDN: Cloudflare, AWS Shield absorb volumetric floods
Per-IP limits: rate-limit by client IP before user auth
Per-user tiers: enforce plan-based limits after auth
Auto-block lists: SET blocked:<ip> 1 EX 86400 checked in middleware
async detectAbuse(userId) { const now = Date.now(); const rapid = await redis.zCount(`requests:${userId}`, now-10000, now); const totalReq = +(await redis.get(`total:${userId}`)) || 1; const failedReq = +(await redis.get(`failed:${userId}`)) || 0; let score = 0; if (rapid > 100) score += 40; // burst if (failedReq / totalReq > 0.5) score += 30; // error rate if (await ipAnomaly(userId)) score += 35; // many IPs if (score > 80) await redis.set(`blocked:${userId}`, 'ABUSE','EX',86400); return score; }
