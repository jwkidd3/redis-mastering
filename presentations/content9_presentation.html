Day 3 - Afternoon Session

The INFO Command: Observability Foundation

INFO # all sections INFO server # version, uptime INFO clients # connected clients INFO memory # memory usage INFO stats # command statistics INFO replication # replication status INFO persistence # RDB/AOF status INFO keyspace # database key counts INFO commandstats # per-command latency
Insurance example: Claims-processing service polls INFO stats every 10s to feed dashboards correlating Redis throughput with claim intake rates.

Key Memory Metrics

used_memory: Total logical memory used
used_memory_rss: OS-resident memory
mem_fragmentation_ratio: RSS / used_memory (ideal 1.0-1.5)
evicted_keys: Keys removed due to maxmemory
INFO memory | grep used_memory INFO memory | grep fragmentation MEMORY USAGE key-name # bytes for a specific key MEMORY STATS # detailed breakdown MEMORY DOCTOR # optimization suggestions
Fragmentation: If mem_fragmentation_ratio > 1.5 consistently, enable active defragmentation or schedule a controlled restart.

Throughput & Latency Metrics

instantaneous_ops_per_sec: Current throughput
total_commands_processed: Lifetime count
keyspace_hits / keyspace_misses: Cache hit rate
latency metrics: P95/P99 response times
INFO stats | grep ops_per_sec INFO stats | grep keyspace # hit_rate = hits / (hits + misses) * 100 LATENCY LATEST # recent latency events INFO commandstats # per-command avg latency
Optimization: Identify the hottest commands in commandstats and apply pipelining, batching, or client-side caching.

Slowlog Analysis

# Set threshold (10ms = 10000 microseconds) CONFIG SET slowlog-log-slower-than 10000 CONFIG SET slowlog-max-len 128 # View recent slow commands SLOWLOG GET 10 # Entry fields: ID, timestamp, exec time (us), # command + args, client info SLOWLOG RESET
Insurance example: A weekly slowlog review on the underwriting cluster caught an unbounded KEYS policy:* scan and replaced it with cursor-based SCAN, dropping P99 from 120ms to under 2ms.
Action required: Commands appearing repeatedly in slowlog must be optimized (better structures, pipelining) or cached client-side.

Client Connection Monitoring

# List all connected clients with details CLIENT LIST # Count connections INFO clients | grep connected_clients # Label your clients for traceability CLIENT SETNAME "quote-service-pod-3" # Inspect current client CLIENT INFO # Terminate a misbehaving connection CLIENT KILL ip:port # Diagnostic — use sparingly! MONITOR
Careful: MONITOR ships every command to the client and can significantly reduce throughput. Use briefly for diagnosis only.

Health Check Endpoint

app.get('/health', async (req, res) => { try { await redis.ping(); const info = await redis.info(); const memoryUsed = parseInfo(info, 'used_memory'); const maxMemory = parseInfo(info, 'maxmemory'); const clients = parseInfo(info, 'connected_clients'); const memoryUtilization = memoryUsed / maxMemory; const isHealthy = memoryUtilization < 0.9 && clients < 900; res.status(isHealthy ? 200 : 503).json({ status: isHealthy ? 'healthy' : 'degraded', uptime: parseInfo(info, 'uptime_in_seconds'), memoryUtilization: `${(memoryUtilization * 100).toFixed(2)}%`, connectedClients: clients, opsPerSec: parseInfo(info, 'instantaneous_ops_per_sec') }); } catch (error) { res.status(503).json({ status: 'unhealthy', error: error.message }); } });
Insurance example: Policy-quote service exposes /health to the load balancer. When memory utilization crosses 90%, the instance is taken out of rotation while an operator investigates.
